# v0.2 design: read-only TCP port ownership

**Status:** design only. Nothing in this document is implemented in v0.1.1.
**Scope:** observe which process owns each listening TCP socket, read-only.

## Why

v0.1.1 infers duplicate development servers from **requested** ports on command
lines. Two `vite` processes can both request 5173 while only one is bound, or both
can be bound on different addresses. That is enough for a cautious prompt, not for
a confident statement. Port ownership turns "these two asked for the same port"
into "this PID is listening on 127.0.0.1:5173 and that PID is not".

It does **not** justify stopping anything, and it does not explain why a process
disappeared.

## API

`iphlpapi.dll` → `GetExtendedTcpTable`.

```
DWORD GetExtendedTcpTable(
  PVOID pTcpTable, PDWORD pdwSize, BOOL bOrder,
  ULONG ulAf, TCP_TABLE_CLASS TableClass, ULONG Reserved);
```

| Parameter | Value |
| --- | --- |
| `ulAf` | `AF_INET` (2) for IPv4, `AF_INET6` (23) for IPv6 |
| `TableClass` | `TCP_TABLE_OWNER_PID_LISTENER` (3) |
| `bOrder` | `TRUE` |
| `Reserved` | 0 |

Call pattern:

1. Call with a null buffer to obtain the required size. The call returns
   `ERROR_INSUFFICIENT_BUFFER` (122) and sets `pdwSize`.
2. Allocate `pdwSize` bytes, call again.
3. Walk the table: a `DWORD` row count followed by fixed-size rows.
4. Free the buffer; no handle is held open.

No socket is created and no packet is sent. The call reads kernel state.

## Row layouts

### IPv4 (`MIB_TCPROW_OWNER_PID`, 24 bytes)

| Offset | Field | Notes |
| --- | --- | --- |
| 0 | `dwState` | listener rows are `MIB_TCP_STATE_LISTEN` (2) |
| 4 | `dwLocalAddr` | network byte order |
| 8 | `dwLocalPort` | **network byte order in the low 16 bits** |
| 12 | `dwRemoteAddr` | 0 for listeners |
| 16 | `dwRemotePort` | 0 for listeners |
| 20 | `dwOwningPid` | process ID, host byte order |

The port conversion must be covered by a fixture test with a known port (for
example 5173 = `0x1435`), because the `DWORD` is little-endian in memory while the
port inside it is in network order.

### IPv6 (`MIB_TCP6ROW_OWNER_PID`, 56 bytes)

| Offset | Field |
| --- | --- |
| 0 | `ucLocalAddr[16]` |
| 16 | `dwLocalScopeId` |
| 20 | `dwLocalPort` (network order, low 16 bits) |
| 24 | `ucRemoteAddr[16]` |
| 40 | `dwRemoteScopeId` |
| 44 | `dwRemotePort` |
| 48 | `dwState` |
| 52 | `dwOwningPid` |

## Multiple listeners and wildcards

- One process can hold many listening sockets: IPv4 and IPv6, several ports, and
  both wildcard and specific addresses.
- One port can appear several times: `0.0.0.0:3000`, `127.0.0.1:3000`, `[::]:3000`,
  `[::1]:3000`.
- `0.0.0.0` and `::` are **local wildcard bindings**, not remote endpoints. They
  mean "all local interfaces".
- The data model must keep rows, not collapse them into a single port value: a
  `PortObservation` holds the port, protocol, addresses and the set of PIDs.
- `SO_REUSEADDR`/`SO_EXCLUSIVEADDRUSE` can allow overlapping binds in specific
  cases. Observe, do not assume exclusivity.

## Privileges and failures

| Condition | Expected handling |
| --- | --- |
| Normal user | Owner-PID table is generally readable; no elevation is requested |
| `ERROR_INSUFFICIENT_BUFFER` | Resize and retry once; then report unavailable |
| `ERROR_ACCESS_DENIED` | Network section unavailable with a reason; the scan continues |
| `ERROR_NOT_SUPPORTED` | IPv6 table unavailable; keep IPv4 results and say so |
| Table grows between calls | Retry once, then report a partial result |
| PID 0 / 4 rows | Record the PID, but do not attribute a project |

StackBroom must never request elevation to improve this data.

## PID reuse and disappearing processes

The process list and the TCP table are sampled at different moments.

1. Read the process list (existing code), including start time where CIM provides
   it.
2. Read the TCP table.
3. Match listeners to processes by **PID and start time**, not PID alone. A PID
   can be reused between samples.
4. If the start time is unknown, mark ownership `inferred`, not `confirmed`.
5. If a listening PID is absent from the process list:
   - report the listener with no process name;
   - do **not** say it "exited", "crashed" or "was killed" — the observation
     cannot distinguish those, and the process may simply be protected.
6. If a process requested a port but no listener exists for its PID:
   - report `requestedPorts` and `listeningPorts` separately;
   - say "requested but not observed listening", never "failed to bind" unless the
     process's own output provides that evidence (it does not here).

## Proposed data model (schema v3)

```jsonc
"network": {
  "available": true,
  "reason": "",
  "ipv4": true,
  "ipv6": true,
  "listeners": [
    { "protocol": "tcp", "family": "ipv4", "address": "127.0.0.1", "port": 5173,
      "pid": 1234, "processName": "node.exe", "wildcard": false,
      "ownership": "confirmed" }
  ],
  "warnings": []
}
```

Per process:

```jsonc
"requestedPorts": [5173],
"listeningPorts": [5173],
"portOwnership": "confirmed"   // confirmed | inferred | unknown
```

`requestedPorts` replaces `ports`, or `ports` is kept as a deprecated alias for
one release. Prefer the rename with a documented migration.

## Effect on duplicate recommendations

| Observation | Recommendation wording | Confidence |
| --- | --- | --- |
| Both PIDs listen on the same port and address family | "Two processes are both bound to port N (one may use a different address family)" | confirmed |
| One PID listens, the other only requests | "PID A listens on N; PID B requested N but is not listening" | confirmed fact, inferred redundancy |
| Both request but neither listens | Keep today's cautious wording; do not claim failure | inferred |
| One listens on IPv4, the other on IPv6 wildcard | Not necessarily a conflict; explain dual-stack | inferred |
| Listening PID is no longer observable | "Listener present, process not observed; no conclusion about why" | unknown |

Risk levels stay unchanged. Ownership never upgrades a recommendation to "safe to
stop": the user still decides.

## Test plan (before implementation)

1. Synthetic `MIB_TCPROW_OWNER_PID` bytes: state, address, port byte order, PID.
2. Synthetic IPv6 rows, including scope IDs.
3. Multiple rows: same port on wildcard and loopback; one PID with several ports.
4. Wildcard `0.0.0.0`/`::` classification.
5. PID reuse: listener PID matches a process but start time differs.
6. Listener PID absent from the process list.
7. Requested port with no listener.
8. `ERROR_INSUFFICIENT_BUFFER`, access denied, IPv6 unsupported.
9. Truncated or absurd row counts: reject rather than allocate unbounded memory.
10. Golden CLI output with a network section present and absent.

The syscall must stay in `*_windows.go` behind an interface, with a
fixture-driven parser in a platform-neutral file, following the existing
`winproc` pattern.

## Performance

Two `GetExtendedTcpTable` calls (IPv4, IPv6) plus at most one retry. Expected cost
is single-digit milliseconds, well below the existing Docker stage (see
`docs/PERFORMANCE.md`). No caching is required for v0.2.

## Non-goals

- No UDP ownership.
- No remote-host inspection.
- No firewall, port-forward or process action.
- No inference about why a process or listener disappeared.
